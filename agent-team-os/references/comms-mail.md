# Comms: Identity Mailbox

The comms layer is an identity-based agent mailbox. It is the durable
record of who said what to whom. Wake mechanisms (see
[doorbell-event-driven.md](doorbell-event-driven.md)) only notify; this
layer stores.

## Concepts

### Identity

Every seat has a fixed mail identity, assigned when the seat is created
and never reused for another seat. Seats are addressed by identity, not
by process, session, or host.

Roles in this package:

| Role | Responsibility |
|---|---|
| coordinator | Owns task assignment and final decisions |
| builder | Implements assigned work |
| verifier | Independently checks builder output |
| operator | Runs deployments and live operations |
| dispatcher | Routes inbound work and monitors queues |

Some servers assign word-pair names (for example `AdjectiveNoun`) instead
of letting you choose an identity. That is fine. Keep a local mapping
table and never address a seat by role alone in a tool call.

Mapping table — keep in the roster, one row per seat:

| Mail identity | Role | Host / location | Notes |
|---|---|---|---|
| `ExampleName` | coordinator | `~/` | |
| `OtherName` | builder | `C:\Users\<you>\` | |

See [../templates/roster.md](../templates/roster.md) for the roster format.

### Messages, threads, and importance

- Every message has a server-assigned `id`. Quote it in replies, logs,
  and handoffs. Do not invent ids.
- Related messages share a thread. A reply stays in the original thread;
  a new topic starts a new thread.
- Importance is `low`, `normal`, or `high`. Use `high` sparingly: it
  affects triage, not delivery order guarantees.
- A message may set ack-required. The recipient must acknowledge it
  explicitly (see below); reading alone does not count.

### Receipts and acknowledgements

Two different signals — do not conflate them:

- **Delivery receipt:** generated by the server when a message lands in
  the recipient's mailbox. Carries a timestamp. Proves storage, not
  reading.
- **Acknowledgement (ack):** generated by the recipient seat when it has
  accepted the message. Carries a timestamp. Proves the seat acted on
  the receipt, not that the underlying task succeeded.

Task success is reported in a separate reply message, with evidence.

### Archive and search

The server is store-and-forward:

- Messages are kept in a durable archive (a versioned store) plus a
  searchable index.
- Full-text search over subject and body is available to seats allowed
  by the contact policy.
- A message that has landed is never lost: server restarts, seat
  restarts, and watcher restarts do not delete it. A recipient that was
  offline reads it on return.

### File reservations

Before editing a shared file, a seat takes a file reservation: an
exclusive lease on a path pattern with a time-to-live (TTL).

- If the lease is held, wait or work elsewhere. Do not edit around it.
- Leases expire on TTL. Expiry does not mean the other seat finished;
  re-check the file before taking over.
- Release the lease when done, rather than letting it lapse, so other
  seats are not blocked unnecessarily.

Reservations prevent two seats editing the same file at the same time.
They do not merge conflicting work.

### Contact policy

A contact policy controls which identities may write to whom.

- Unknown or unapproved identities cannot deliver mail until approved.
- System notifications about contact approvals and requests are
  administrative events, not task mail. The doorbell skips them; see
  [doorbell-event-driven.md](doorbell-event-driven.md).
- Tighten the policy for seats that only need to talk to the
  coordinator; leave it open only inside a trusted team.

## Core operations

Three operations cover normal use: `send`, `reply`, and `ack`.

| Operation | Effect | Who may perform it |
|---|---|---|
| `send` | Creates a new message and thread, addressed to one or more identities | Any approved identity, subject to contact policy |
| `reply` | Adds a message to an existing thread, referencing the original message id | A recipient of the thread, or an approved participant |
| `ack` | Marks a specific message acknowledged by the calling identity | Only the addressed recipient of that message |

Rules:

1. Reply in-thread for follow-ups. Do not start a new thread to answer
   an old one.
2. Ack only messages addressed to you, and only after you have read
   the full body.
3. If a message requires action you cannot take, reply saying so. Do not
   ack and stay silent.
4. Include evidence in completion replies: file paths, hashes, or
   command output references. A bare "done" is not a report.

## Access patterns

### MCP-native seats

Seats with a native tool integration call the mailbox tools directly:
send, reply, ack, search, and reservation calls are tool invocations in
the seat's session. No helper script is needed.

### Non-MCP seats: helper script

Seats without a native integration use a thin helper script that
performs one tool call per invocation over the mailbox's HTTP JSON-RPC
endpoint. The wire contract the server must implement — endpoint,
tool shapes, receipts, and the delivery-event stream — is specified
in [mail-server-interface.md](mail-server-interface.md); the mailbox
server itself is an external dependency and is not shipped in this
package.

Reference implementation:
[../templates/scripts/mail-helper.ps1](../templates/scripts/mail-helper.ps1)

Pattern:

- Endpoint: `{{MAIL_SCHEME}}://{{MAIL_HOST}}:{{MAIL_PORT}}/` for
  project `{{PROJECT_KEY}}`. The scheme is a deployment setting:
  `https` wherever the server offers it; `http` only on a trusted
  network, because the bearer token travels in the Authorization
  header (see [mail-server-interface.md](mail-server-interface.md)).
- Transport: HTTP POST, JSON-RPC, one method per call.
- Authentication: bearer token read at runtime from a local token file
  in the seat's home directory (for example `~/mail-token.txt` or
  `C:\Users\<you>\mail-token.txt`).
- The token is never printed, never logged, and never committed to a
  repository. Rotate it if it appears in any output.

Helper parameters:

| Parameter | Meaning |
|---|---|
| `action` | `send`, `reply`, or `ack` |
| `from` | Calling seat's mail identity |
| `to` | Recipient mail identity (for `send`) |
| `subject` | Subject line (for `send`) |
| `body` | Message body, verbatim |
| `messageId` | Original message id (required for `reply` and `ack`) |

Example invocations (shape only):

```powershell
# send
mail-helper.ps1 -Action send -From ExampleName -To OtherName `
  -Subject "Task: example" -Body "See task card."

# reply
mail-helper.ps1 -Action reply -From OtherName `
  -MessageId 42 -Body "Done. Evidence: ~/output/result.txt"

# ack
mail-helper.ps1 -Action ack -From OtherName -MessageId 42
```

A robot / CLI surface provided by the mailbox server can be used
instead of the helper, with the same parameters and the same token
rules.

## Store-and-forward guarantees and limits

Guaranteed, once a send call returns success:

- The message is in the durable archive and the searchable index.
- A delivery receipt with a timestamp exists.
- The message survives server and seat restarts.
- Recipients can read it later, in thread order.

Not guaranteed:

- **A send attempted during an outage is not queued on the client.**
  There is no offline client queue. If the server is unreachable, the
  send fails and the sender must retry after the server returns.
- Delivery receipt does not mean the recipient has woken, read, or
  acted. That is what ack and the doorbell are for.
- Search reflects landed messages only; a failed send is not findable.

Operational rule: check the return value of every send. A failed send
is a failed handoff until retried successfully.

## Known limitations

### Self-declared sender on CLI-originated calls

On calls that originate from a CLI or helper script, the sender field
is self-declared and the server does not cryptographically verify it.
Responses on that path report `verified_sender: false`.

Consequence: identity assurance on that path equals possession of the
shared bearer token. Anyone holding the token can send as any identity.

- Acceptable: a single trusted team on a private network, where the
  token is the trust boundary.
- Not acceptable: adversarial settings, multi-tenant use, or any flow
  where a message alone authorizes payment, deployment, or credential
  release. In those flows, require out-of-band confirmation by the
  coordinator regardless of the claimed sender.

### Send during outage

As above: no offline queue. A send attempted while the server is down
fails at the client and is lost unless the sender retries. Senders that
run unattended must log the failure and retry on their next run, or
surface it to the operator.

### Other limits

- File reservations are advisory coordination, not filesystem locks.
  A process that ignores reservations can still write the file.
- Ack proves acceptance, not correctness. Verification is a separate
  seat and a separate step; see [verification.md](verification.md).
